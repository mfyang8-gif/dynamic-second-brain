# 2026-10-12（傍晚）—— 语义记忆链路的口径澄清（易误解，务必记住）

用户提问「习惯提取入 qdrant 是三次前还是三次后、三次才进 mysql 吗」，读源码后确认三条口径，
**这套说法最容易被记反，后续讨论必须以本节为准**：

1. **Qdrant 在本项目只是「写入端查重索引」，不是长期记忆的存储。**
   `user_semantic_habits` 集合只在 `SemanticMemoryServiceImpl.resolveFinalHash()` 里被 `searchByDenseSimilarity`
   用于宽召回（阈值 0.60、limit 3）；**消费端（`getUserGlobalMemory`）完全不碰 Qdrant**，是纯 SQL。
   → 与 Mem0 等把向量库当记忆主存储 + 消费端检索的方案，**向量库的定位完全不同**。
2. **MySQL 是两张表，"三次"只约束后者：**
   - `user_semantic_candidate`（候选池）—— **第 1 次提取到就 upsert 落库**，`hit_count=1`；`ON DUPLICATE` 累加；
     另有 30 天 TTL 懒清理（`last_hit_at` 过期且未晋升即物理删除）。
   - `user_semantic_memory`（正式记忆 = 长期记忆）—— 只有 `hit_count >= 3` 且 `promoted=0` 才 `INSERT IGNORE` 晋升。
   → 「三次后才进 MySQL」不准确；准确说法是「三次后才进**正式记忆表**」。
3. **入口时机与次数无关：** `SemanticScanProducer.armSessionScan()` 在每轮落库后武装一次延时消息
   （RabbitMQ TTL 300s + DLX），Redis `semantic:scan:armed:{sessionId}` 冷却锁保证 **N 轮只调度一次**；
   消费时取最近 10 条 user 消息（<2 条跳过）。即「**会话静默 5 分钟**」触发，不是「第 3 次对话」触发。
   `hit_count` 的语义 ≈ 「跨几个静默窗口复现」——同窗口变体由 `touchedHashes` 拦掉重复计数。
4. **Qdrant 写入时机**：`finalHash.equals(exactHash)` 时才写（全新习惯必写；召回 miss 但 MySQL 有行时重写以自愈漂移）；
   命中他人旧 hash 时不写（该向量本就在库里）。pointId = `userId:factHash`（必须带 userId 命名空间，否则跨用户同措辞互相覆盖）。
5. 改口处理：`HabitJudge` 明确把「偏好 Vue3 vs 偏好 React」判为**不相同** → 新旧两条并存，**我们没有 UPDATE/DELETE**。

### 客户端侧关键事实（已逐文件核实，别再猜）
- 栈是 **LangChain4j 1.15.0-beta25 + Spring Boot 3.4.0 + Java 21**（**不是 Spring AI**）。
- 已有共享 `RestTemplate`（connect 5s / **read 60s**，用于 Pandoc/Rerank）→ **绝不可复用**调 Graphiti，会把 MQ 消费线程钉死 60s。
- `@EnableRetry` **已在** `MiniNodepadApplication`，`AbstractStudioGenerator` 已用 `@Retryable` → 声明式重试零新增依赖。
- **选型结论：`RestClient` + 独立 `RestClient.Builder` + 独立 ObjectMapper**。理由：调用点全阻塞（MQ 线程/虚拟线程内同步编排），WebClient 只会逼出 `.block()`；OpenFeign 要引整条 Spring Cloud（工程零 Spring Cloud 依赖），且 Feign 自带重试会与 `@Retryable` **叠乘**实际调用次数。
- ★ **致命陷阱（实测分析）**：`json/JacksonObjectMapper` 是 `@Primary`（`WebMvcConfiguration:72-75` 注册），把 `LocalDateTime` **钉死为 `yyyy-MM-dd'T'HH:mm:ss`**；而 Graphiti 返回 `2026-10-12T09:51:56.345970+00:00`（微秒+offset）→ **用 `LocalDateTime` 必解析失败**。DTO 必须用 **`OffsetDateTime`**，且 Graphiti client 自建 ObjectMapper 与 Web 层解耦。
- 禁用全局 `SNAKE_CASE`：会波及所有 VO/DTO，破坏前端契约。用 `@JsonProperty` 局部标注。
- 注入点 = `ChatStreamService.buildUserMemoryBlock()`；路由 = `IntentRoutingService` 五分类（已是管线第一节点，召回分流可白嫖）。
- **`UserIntent.EPISODIC_MEMORY` 分支注释写着「记忆检索 gap 本轮不修」→ 这就是 Phase 4 要补的洞**。

### 服务端契约（从容器源码补齐了 OpenAPI 没有的部分）
- `ingest.py:59-68`：`episode_body = f'{role}({role_type}): {content}'`（**content 会被包一层**）；`reference_time = m.timestamp`（**不传则服务端 `utc_now()`**，会让时间线漂移）；`uuid = m.uuid`（可作幂等键 + 落库确认比对键）；`name` = episodic node 名；`source_description` 独立字段。
- `dto/common.py:25`：`timestamp` 有 `default_factory=utc_now` → **必须显式传**。
- `FactResult`（`dto/retrieve.py:16-29`）**无 `group_id`** → 客户端无法自证 fact 归属。
- `SearchQuery.group_ids` = `list[str] | None = None`，**只有 query 必填**。
- `POST /clear` 无参数 = **整图清空**；按组清理用 `DELETE /group/{id}`；遗忘单条用 `DELETE /entity-edge/{uuid}`。
- `/get-memory` 契约已定：需 `group_id`(单数) + `center_node_uuid` + `messages` → **本 Phase 不用**。

### MQ 侧（现有隐患 + 新设计）
- 现有 `semantic.scan.queue` **未声明 DLX** + `default-requeue-rejected=false` → 抛异常 = **静默丢弃无痕迹**；`SemanticScanConsumer` 是 catch-all 吞异常 → **完全没有重试**。这三条建议顺带修。
- 新拓扑 `graphiti.write.*`：exchange / queue(DLX→dlx) / retry 队列（**3 个静态 TTL 队列 30s/2min/10min**，单队列动态 TTL 会队头阻塞）/ dlx / dlq。
- 失败分类：**400/422 是毒消息 → 直接 DLQ 不重试**；连接拒绝/超时/5xx → 最多 3 次退避。
- ★ **MQ 重试不要用 `@Retryable`**（同线程循环、重试期间消息未 ack 占住消费者）；要交给 TTL+DLX 把重试卸载到 broker。
- ★ **202 ≠ 成功**：`POST /messages` 返回时 episode 还没进 Neo4j（实测首条 21~45s）。推荐**轮询 `GET /episodes/{group_id}?last_n=N` 按 uuid 比对**确认，窗口 90s；只比数量是弱判据。
- 并发度建议 `concurrency=1 / prefetch=1`（服务端 `AsyncWorker` 是单协程串行）。
- ⚠️ 新消息类必须登记进 `RabbitSemanticConfig.jacksonMessageConverter()` 的 `addTrustedPackages`（**包名精确 equals**，不登记会被静默丢弃 —— 该文件 66-75 行有血泪注释）。
- **待验证项（B1 第一件事）**：`Message.uuid` 重复投递时 graphiti-core `add_episode` 是抛错/覆盖/重复建边？决定幂等方案能不能只靠 uuid。

### ★★ 本轮读源码纠正的两个致命认知（否则方案会落空）
1. **`messages[]` 不是"一个 episode"**：实读 `/app/graph_service/routers/ingest.py` →
   `for m in request.messages: queue.put(partial(add_messages_task, m))`，**每条 message 独立成 episode**，各自带 `uuid`（客户端可指定）与 `reference_time = m.timestamp`。
   ⇒ ① 双时间戳裁决粒度 = **单条消息**；② **`timestamp` 必须显式传**（`default_factory=utc_now` 会把历史对话盖成"处理时刻"，裁决直接失效）；
   ③ 一次 POST 带 N 条 = **N 次串行 add_episode**（AsyncWorker 单协程），实测 20~45s/条 → **批次上限 3 轮**。**推翻了我上一轮"5min 整批 = 一次 POST 很划算"的结论。**
2. **Qdrant 里从来没有"对话流水账"**：`application.yaml` 的 collections 只有 `dynamic_brain`（**上传文档切片**，indexes: bookId/userId/pageId/createdAt）
   + `user_semantic_habits`（习惯查重索引，**本次废弃**）。用户风险一举的例子（"那句话进了 Qdrant 流水账"）在当前代码里**不成立** —— 对话原话在 MySQL `chat_message`。
   ⇒ 风险一的真实形态是 **「笔记/资料 vs 图谱事实」**（长期存在、当前完全没处理）+ **「L1 历史原文 vs 图谱事实」**（窗口小，通常已滚出），**不是 Qdrant 打架**。

### ★ 风险二（5 分钟失忆症）的认知纠正
- L1 实为 `MessageWindowChatMemory`，yaml `chat.memory.max-messages: 6` ⇒ **是「条数窗口」不是「时间窗口」**，
  用户说的"至少保留 15 分钟"在实现层**不成立**（密集对话 5 分钟就超 6 条，事实照样被挤掉）。
- `RedisChatMemoryStore` 只配了 host/port、**未显式设 TTL**（默认值待实测）。
- 真正"永不丢"的持久层是 **MySQL `chat_message`**（`SemanticScanConsumer.fetchRecentUserTurns()` 就是从它读）。
- 兜底三条：① `max-messages: 6 → 20` + TTL 显式化；② **新增「未沉淀原文」时间窗**（召回时从 `chat_message` 取最近 N 分钟，块首标 `[尚未沉淀为长期记忆的近期对话]`）；
  ③ 可选热点快通道（落库后立即跑判定器，命中即提前 30s 投递，真空期 5min → ~40s），建议一期不做。

### ★ 契约原文（容器内实读 `dto/common.py` / `dto/retrieve.py`，比 `/openapi.json` 更准）

### ⚠️ 我必须纠正自己的预判：中文 BM25 **能命中**，但**分数不可用**

### ★★ 快通道必然导致「同一条消息被投两次」（真正的漏洞）
- 常规链路 `armSessionScan` → 5 分钟后 `fetchRecentUserTurns()` **取最近 10 条 user 消息**；快通道投过的那条**必然被再捞一次** —— **是必然，不是概率**。
- `add_episode` 每次都**独立跑 LLM 抽取 + 边解析**：episode 节点可能 MERGE（幂等），**但边不保证去重** → **不能依赖 `uuid` 幂等**（它只能当第二道防线）。
- **确定性解法：`chat_message` 加 `graphiti_synced_at`**（NULL = 未投递）：
  ① 投递前查 `IS NULL`，投递后**同事务** UPDATE；② `fetchRecentUserTurns()` 改 `WHERE graphiti_synced_at IS NULL`；
  ③ 附带全是好处：**可观测**（SQL 直查"哪些还没进图"）、**可补投**（服务恢复后扫 NULL 历史消息）、**可审计**。

  改为写**人话式来源说明**：`用户消息（命中高危词：过敏，提前投递）` —— 保留审计能力且不污染语义。`name` 字段实测全为空串、完全空闲，是备选载体。

### P6 前置核验：作废事实的过滤判据（已实证，直接影响实现）
- **判"当前有效"只需看 `invalid_at`，不必看 `expired_at`**。证据三源：① `graphiti_core/search/search_helpers.py:57` 官方口径「valid = invalid_at 为 Present」；② `expired_at` 三条赋值路径（`utils/maintenance/edge_operations.py:569 / 822 / 838`）全部与 `invalid_at` 同时写入；③ Neo4j 直查 10 条边 `ia_only=0 / ea_only=0`。
