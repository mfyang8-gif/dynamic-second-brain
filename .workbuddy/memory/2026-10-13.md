### ⛔ 本轮实机验证抓到两个 P0（静态审查不可能发现，且都是静默失效）

| # | 症状 | 根因 | 后果 | 修法 |
|---|---|---|---|---|
| **P0-1** | `Incorrect DATETIME value: '+1000000000-01-01 00:00:00'`（error 1525） | `GraphitiScanConsumer.resolveWindowStart` 用 `LocalDateTime.MIN` 当「无水位」哨兵，而 MySQL `DATETIME` 定义域只有 1000-01-01 ~ 9999-12-31 | **每个新会话的首次扫描必炸**（首次扫描无 Redis 水位 → 必走 MIN 分支）→ reject 不 requeue → 进 DLQ → 发现层对全新会话完全不工作，对外只表现为「记忆一直不生成」 | 换 `EPOCH_FLOOR = 1970-01-01`（在定义域内） |
| **P0-2** | `Illegal mix of collations (utf8mb4_0900_ai_ci) and (utf8mb4_unicode_ci)`（error 1267） | 我的 DDL 只写 `DEFAULT CHARSET utf8mb4` 没写 `COLLATE` → MySQL 8 默认 `utf8mb4_0900_ai_ci`；而本库既有表全是 `utf8mb4_unicode_ci`（RuoYi 老约定） | `a.message_id = c.id` 列 vs 列比较直接抛错 → **Confirm/Replay 两条对账 SQL 每轮必炸** → 消息永远确认不了 → 全走到 maxRounds 被误判 `CONFIRM_TIMEOUT` 隔离 → **写入链静默退化成「只投不认」** | 建表显式 `COLLATE=utf8mb4_unicode_ci`；DDL 附幂等 `ALTER TABLE ... CONVERT TO ...`（已执行） |

**两条可复用的教训**：
1. **Java 的极值常量不是 SQL 的极值常量**。凡把 `MIN`/`MAX` 哨兵绑进 SQL，先查目标列类型的定义域。
2. **跨表列比较的排序规则不一致，自查极难发现** —— `existsByMessageId`（绑定变量 vs 列）**不会**报错
   （参数 coercibility=4，列=2，列胜出）。**只有「列 vs 列」的子查询才暴露**。
   凡新增表，必须检查**每一条跨表列比较**，而不是「有没有用过那张表」。

### 三个「工具/流程骗了自己」的坑

1. **RabbitMQ `messages_ready` 是 5 秒快照统计**（`collect_statistics_interval` 默认 5000ms）→
   用它判断「刚清空」会看到假残留 `ready=1`。**量真实条数必须用
   `POST /api/queues/%2F/{q}/get` + `ackmode=ack_requeue_true`。**
2. **`/episodes` 只有路径形式** `GET /episodes/{group_id}?last_n=N`。写成查询参数
   `/episodes?group_id=…` 返回 **404**，看起来像「这个用户没有数据」→ 我据此误判
   「10-12 的实测数据被清空了」。**一个 URL 形式写错能让你得出与事实完全相反的结论。**
3. **图谱是有状态的 → 测试必须自己清分区**。夹具用固定 message id，上一次运行遗留的
   `cm_<id>` episode 会让本轮「等服务端落库」**第一轮就命中** → 测试全绿但落库耗时是假的。
   实测到过两条同名 episode（created_at 相隔 6 分钟）。→ `fixture()` 第一步必须
