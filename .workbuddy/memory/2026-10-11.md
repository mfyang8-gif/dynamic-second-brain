## 零点加急：行内公式「带空格定界符」不渲染（用户截图报障）

**现象**：`$ y_i $`、`$ \log(p_i) $` 这类 LLM 常见输出（$ 定界符内侧带空格）
整段原样露出，看着像乱码。

**根因**：昨晚重写的行内规则沿用 Pandoc 严格口径——开 $ 后不能紧跟空白、
闭 $ 前不能是空白（防货币误判）。LLM 恰恰爱带空格输出，整对失配 → 原文直出。

**修复（markdown.ts mathInlineRule 两层匹配）**：
- 严格档优先（原逻辑不变）；
- 宽松兜底档：严格失配后放宽空白限制，但必须同时过两个反误判闸门——
  (a) 内容含真 LaTeX 信号字符（`\ _ ^ { }` 之一），纯金额/纯中文不带；
  (b) 闭 $ 后不紧跟数字（防「$ 5 和 $ 10」金额区间被吞）。
- MATH_SIGNAL_RE 常量 + 注释同步更新。

**回归**：`_cdp_math_probe.mjs` 用例扩到六场景 12 断言全过
（katex=5：严格2 + 带空格2 + 病态红色渲染1；金额区间保持原文）；
`_cdp_stream.mjs` 114 断言 ×3 主题全过，无副作用。

**教训**：LLM 输出的数学定界符【经常内侧带空格】，严格 Pandoc 口径会把
大量真公式漏成原文。宽松必须有反误判闸门，且反向用例（金额区间）要进回归。

## ★ 语义记忆链路「表全空」根因：MQ 白名单包名不匹配导致消息被静默丢弃

**现象**：3 个会话各 2 条 Vue3 习惯语（`MIN_MESSAGES_TO_SCAN=2` 已满足、消息确实落
`chat_message`），5 分钟后延时队列 6→0 正常清空，但 `user_semantic_candidate`
与 `user_semantic_memory` **始终 0 行**，Qdrant `user_semantic_habits` `points_count=0`。

**取证方法（关键，不依赖后端日志）**：
1. RabbitMQ 管理 API 拉 `/api/queues/%2F/semantic.scan.queue` →
   `deliver=6` 但 **`ack=0`、`redeliver=0`、队列已空** —— 投递了却既没 ack 也没重投。
2. Redis `semantic:consume:*` **一个都没有**（本机 21:06 查，TTL=10min，消费若发生在
   21:01–21:04 必然还在）→ 说明**监听器方法体从未执行**（幂等键写在方法第一行）。
3. 对照探针（向 `semantic.scan.exchange` / routing key `scan` 直投，
   显式带 `__TypeId__` 头）复现失败：`deliver+1 / ack+0`；
   **去掉 `__TypeId__` 头则 `ack+1`** → 头就是凶器。

**根因**（`javap -c` 字节码核实，非猜测）：
- `RabbitSemanticConfig` 里 `addTrustedPackages("com.yangmf.mini_nodepad")` 写的是**父包**，
  而 `DefaultJackson2JavaTypeMapper.isTrustedPackage` 是
  `packageName.equals(trustedPackage)` —— **精确相等，不认前缀**！
  `SemanticScanMessage` 包名 `com.yangmf.mini_nodepad.mq` ≠ 白名单项 → 不可信。
- `getClassIdType` 抛 `IllegalArgumentException`（"not in the trusted packages"）
  → 转换器包装成 `MessageConversionException`；
- `ConditionalRejectingErrorHandler$DefaultExceptionStrategy.isCauseFatal` 里
  `instanceof MessageConversionException` → **true（致命）** → `basic.reject(requeue=false)`；
- 叠加 `spring.rabbitmq.listener.simple.default-requeue-rejected: false` →
  **消息静默丢弃、永不重投**。所以延时队列“正常清空”是假象：消息走进死信路由后
  在消费端被吃掉。Consumer 的 `catch(Exception)` 兜不住（异常发生在方法调用之前）。

**修复**：白名单改成**精确包名** `com.yangmf.mini_nodepad.mq`（+ `...pojo.dto` 备用）。
已加注释警示：今后每新增一个承载 MQ 载荷的包都要在此显式登记。

**通用教训**：
- Spring AMQP 的 `addTrustedPackages` 是**精确包名**语义，写父包无效。
- 「队列清空」不等于「消费成功」——必须同时看 `ack` 计数与业务副作用（Redis 键/DB 行）。
- `default-requeue-rejected=false` 会把一切失败（含转换失败）变哑，排障时要意识到这点。
- 该白名单同时挡住反序列化 gadget 面，改错方向（如改成 trust all `*`）会开安全口子，
  正解是登记准确包名。

**验收脚本**：`mini-notebooklm-web/_verify_fix.py`（不用等 5 分钟 TTL，向交换机直投
3 条模拟死信产物，秒级判定：1 行 hit_count=3 promoted=1 → PASS；3 行各为 1 →
说明向量相似度未达 0.85，再去降 `semantic.dedup.similarity-threshold`）。
另有取证脚本 `_diag_semantic.py`（全链路快照）、`_probe_scan.py`（转换对照探针）。

### 修复后复测：第 1 个 BUG 已确认消灭，但暴露出第 2 个阻断

- C. fact 之外让 LLM 额外输出归一化 `habitKey`（如 `frontend-framework:vue3`），

（用户改口时旧习惯被强化而非新建记忆）。

### ⚠️ 顺带修掉一个多租户缺陷：Qdrant 点 ID 未带 userId 命名空间

**发现方式**：跑完 `SemanticDedupJudgeTest`（user_id=999）后，demo(3) 的 4 个向量点只剩 2 个。

**根因**：`writeHabitVectorQuietly` 原先把 `factHash` 直接当 pointId，而
`QdrantTemplate.toQdrantUuid` 是对该字符串做 `UUID.nameUUIDFromBytes`（v3/MD5）——
**pointId 只由 fact 文本决定，与 user_id 无关**。两个不同用户说出**措辞完全相同**的习惯时
会落到同一个点，后写者覆盖前者的 `payload.user_id`；前者此后按 user_id 过滤就**召不回自己的向量**，
跨表达召回间歇失效，并在两人之间来回乒乓覆盖。方案 B 依赖召回准确性，故此缺陷必须修。

**修复**：pointId 改为 `userId + ":" + factHash`（新增私有方法 `vectorPointId()`）；
payload 里的 `fact_hash` 仍存**纯 hash**（它是回查 MySQL 的键）。

**数据修复**：新增 `test/.../SemanticVectorRebuildTest.java` —— 一次性运维工具，
只读 MySQL 候选行 → 按新 pointId 全量 upsert 向量，**不动任何计数**。
执行前需先清空集合旧点位（旧格式不含 userId 前缀，会与新点并存成重复）。重建后 4 条向量归位。

**验证**：重跑 `SemanticDedupJudgeTest` → `59041b57` 与 `7c031ac8` 两个 hash 各自拥有
user_id=3 / user_id=999 两个**独立点**（互不覆盖），demo(3) 点数稳定为 4，路由测试仍 PASS。

**教训**：把「确定性业务键」直接当向量库 pointId 时，**必须把租户维度并入 ID**，
否则 payload 上的租户字段会在 upsert 时被别的租户改写。测隔离性不能只测 MySQL。

### 架构组复核结论 + Point ID 规范问题的正解

架构组问「`vectorPointId` 返回 `"3:59041b57"` 这种普通字符串，Qdrant 会不会因格式非法报错，
要不要自己套一层 `UUID.nameUUIDFromBytes`」。**结论：底层已做，且不能再套。**

- `QdrantTemplate.upsert` 第 89 行：`Common.PointId.newBuilder().setUuid(toQdrantUuid(pointId))`，
  而 `toQdrantUuid`（第 414 行）就是 `UUID.nameUUIDFromBytes(id.getBytes(UTF_8)).toString()`。
  凡经过 `QdrantTemplate` 的 ID 全部被统一映射成合法 UUID，调用方传什么字符串都安全。
- **绝不能自己再套一层**：`QdrantTemplate.delete` / `fetchChunkTextsByIndexes` 走的也是同一个
  `toQdrantUuid`。若调用方先把 `"3:hash"` 变成 UUID 再传进去，delete 会把这个 UUID **再哈希一次**，
  写入键与删除键算出两个不同 UUID → 删除功能静默失效。
- 通用判据：**确定性 pointId 的归一化只应发生在最底层一处**，上层只管传业务键。

### 缺陷 2（**已复现，暂未改，待用户裁决**）：regenerate 重发会重复插入 user 消息

对历史上真跑过 regenerate 的会话 `bb074efa50dd5104e3130a2e83851923` 查时间线（实证）：
```
12:57:58.715  user        deleted=0   用一句话说明什么是依赖注入。
12:57:58.751  assistant   deleted=1   ← regenerate 截断的旧回答
```

- `ChatSessionServiceImpl.regenerate` 截断条件是 `.ge(created_at, target.createdAt)`，

- `ChatStreamService.persistMessages()` 第 641 行**无条件**再插一条 user 消息（无任何
  regenerate 分支判断）；`saveMessage` 也是裸 insert，无去重。

影响：会话内看不出（前端由本地 `messages` 驱动），但**页面刷新/首次加载**走
`GET /messages` 会把两条相同提问都渲染出来 → 用户看到问题气泡重复；
ChatMemory 里也会出现连续两条相同 user turn。

建议补丁（动的是核心流式管线，故**未擅自改**，请裁决）：
把 `resolveRegenerateInstruction(token)` 改为返回「指令块 + 是否真的消费了 token」的小结果，
再给它加一个布尔出口透传到 `persistMessages(..., skipUserMessage)`；
`skipUserMessage = true` 时跳过第 641 行那次 user 落库（assistant 照常落）。
本前端 `syncBackendIds` 已用「正文优先」对齐，**多出的那一行不会错配主键**，所以前端暂时不受影响。
