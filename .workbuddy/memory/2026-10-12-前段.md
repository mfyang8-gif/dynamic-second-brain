- ★★ **另一处认知纠正**：**Qdrant 里从来没有"对话流水账"**。`application.yaml` 的 collections 只有 `dynamic_brain`（上传文档切片）+ `user_semantic_habits`（习惯查重索引，本次废弃）。用户风险一举例的"那句话进了 Qdrant 流水账"在当前代码里不成立 —— 对话原话在 MySQL `chat_message`。真实冲突是 **笔记/资料 vs 图谱事实**（长期存在）与 **L1 历史原文 vs 图谱事实**。
- ★★ **风险二的认知纠正**：L1 是 `MessageWindowChatMemory`，yaml `chat.memory.max-messages: 6` → **是「条数窗口」不是「时间窗口」**，"至少保留 15 分钟"在实现层不成立（密集对话 5 分钟就超 6 条）。且 `RedisChatMemoryStore` 未显式设 TTL（默认值待实测）。真正"永不丢"的持久层是 MySQL `chat_message`。兜底 = ① 窗口 6→20 且 TTL 显式化；② 新增"未沉淀原文"时间窗（from `chat_message`，默认 10min）；③ 可选热点快通道。
- 契约原文（`dto/common.py` / `dto/retrieve.py`，**比 OpenAPI 更准**）：
  - `Message.role: str | None = Field(description=...)` **没有 default → pydantic 视作必填**（可为 null 但字段必须出现），不传 role 会 422。`timestamp: datetime = Field(default_factory=utc_now)`。
  - `FactResult`：`uuid, name, fact, valid_at(可空), invalid_at(可空), created_at(**非空必填**), expired_at(可空), source_node_uuid, target_node_uuid, episodes[]`；**无 group_id**；时间序列化 = `astimezone(UTC).isoformat()`（微秒+offset）→ Java **必须 OffsetDateTime**。
  - `SearchQuery.group_ids: list[str] | None = None`（可空）、`query` 必填、`max_facts=10`。
  - 存在 `GET /entity-edge/{uuid}`（单条详情）、`DELETE /episode/{uuid}` → 事后清洗闭环可用。
- 方案要点：`RestClient` + 自建 ObjectMapper（不复用 60s 超时的 restTemplate）；过滤放 Client 唯一出口（`RecalledFact` 类型上就没有 invalidAt）；MQ 复用现有 TTL+DLX 骨架但必须先修三隐患（无 DLX / catch-all / armed 无条件释放）并加**扫描水位**；重试 3 个静态 TTL 队列 + DLQ，毒消息(400/422)不重试；**202≠成功**要按 uuid 轮询确认；召回做**双 query 并行**（画像固定 query 可缓存 + 情景 query），硬预算 800ms；Prompt 加 `{{episodicMemory}}` 槽位 + 记忆权重铁律 + `{{context}}` 块首"资料≠用户事实"声明。
- 待拍板收敛到 8 项（P1~P8），含"是否给 `EPISODIC_MEMORY` 扩为跨会话回溯+画像"（产品语义变更）。
- 工具坑复现：Docker `/containers/json` 的 `Names` 形如 `['/memory_graphiti']`（**带前导斜杠**），用 `name in Names` 判断会永远 False → 必须 `any(name in n for n in Names)`。

## 2026-10-12（续2）invalid_at vs expired_at 语义核验（Graphiti 作废判据）
- 起因：怀疑 v2 方案"只判 invalid_at 过滤无效事实"漏了 expired_at。
- **结论：没漏，只判 invalid_at 是正确且充分的。** 三源交叉：
  ① `graphiti_core/search/search_helpers.py:57` 官方口径原文 —— "Facts with an **invalid_at** date of 'Present' are considered valid"（expired_at 根本不出场）；
  ② `expired_at` 仅有 3 条赋值路径，**全部紧贴 invalid_at**：`utils/maintenance/edge_operations.py:569-570`（被新边作废：invalid_at=新边valid_at、expired_at=utc_now()）、`:822-823`（补账：invalid_at 有而 expired_at 空则补 now）、`:838-840`（新边被更晚候选作废）；
  ③ Neo4j HTTP 直查全部 10 条 RELATES_TO 边：has_ia=2 / has_ea=2 / **ia_only=0 / ea_only=0** / both_null=8。
- 语义差异（实测 14~16s 差）：`invalid_at` = 事实**业务上失效**时刻（可远早于系统处理）；`expired_at` = 图里**登记为失效**的系统时刻。展示"你何时改的口"要用 invalid_at。
- ⚠️ 上游文档 bug：`edges.py:271` 把 expired_at 描述写成 "datetime of when the **node** was invalidated"（应为 edge；且措辞与 invalid_at 的 "stopped being true" 混淆）→ 照字段描述实现的人会误以为 expired_at 才是作废标记。
- ★ 意外发现：**新写入的边可能当场被作废** —— `edge_operations.py:838-840`：若库中已存在 valid_at 更晚的候选边，新边立刻 `invalid_at = candidate.valid_at`。"写入成功 ≠ 事实生效"，故投递成功判据**不能**用"新边 invalid_at 为空"，只能用 uuid 存在性。
- 好用技巧：Neo4j HTTP Cypher 直查 `POST http://192.168.88.130:7474/db/neo4j/tx/commit`（basic `neo4j:password123`，body `{"statements":[{"statement":"..."}]}`），**不必 exec 进容器**。Docker exec 的 start 端点用简写 `/exec/{eid}/start`（写成 `/containers/{cid}/exec/{eid}/start` 会 400）。

### ★ 异步 MQ 消费 + LLM 服务集成的通用坑（Phase 4 评审补丁提炼，跨项目适用）
- **防重机制必须可超时释放**：Redis `setnx` + TTL 1h 做 MQ 幂等 → 消息进重试队列 30s 后回来、锁还在 → **被自己的防重永久拒收**（整条重试链瘫痪）。正解：**DB 事前 CAS 占位**（`WHERE col IS NULL OR col < now()-3min`）+ **可重试异常必须回滚占位**；毒消息（400/422）才保留。
- **CAS 占位必须在「发起请求之前」**，不是之后 —— 否则 ack 丢失导致的重投会在"写状态位之前"再发一次 → **重复副作用**。
- **异步架构下 429 有盲区**：`POST` 返回 202 后真正的 LLM 调用在服务端 worker 里，客户端**看不到 429**，只表现为"结果迟迟不出现"。→ 限流防御要**同时在【投递层】和【对账/确认层】做两处**。
- **限流绝不可归入「4xx 毒消息」**：否则高峰期成批进 DLQ 永久丢失。判定要**同时看状态码 + body 关键词**（服务端常把上游 429/配额错误包装成 500 或别的 4xx）。
- **服务端不过滤「已失效」数据时，客户端必须宽拉取**：要 N 条 → 服务端按相关性返回 N 条 → 客户端过滤掉已失效的 → 可能**一条不剩**（有效的那条排在第 N+1 位、从未被拉回）。正解：`请求 max = limit × FETCH_FACTOR`，**截断必须在过滤之后**。
- **用「最近 N 条」做对账/确认窗口时，N 必须动态算**：固定 N 时目标项会被更晚的项挤出窗口 → 误判失败 → **无限重投**（确定性必然发生，不是概率）。
- **多路召回禁止「合并后全局排序再截断」**：不同来源的"时间尺度"不可比（长期画像 vs 近期情景），单一维度全局排序必然**踩踏**。正解：**独立过滤、独立截断、物理分槽**。
- **背压熔断的信号别用 DLQ 深度**：DLQ 只在重试全失败后才涨，等它涨说明数据已丢。用**主队列积压 + 未确认数**；熔断要**可自动恢复**（否则是故障不是保护），并设计成**延迟而非丢弃**（配合状态位，恢复后自动补投）。
- **RabbitMQ 优先级队列（`x-max-priority`）只在队列积压时生效**（消费者空闲时消息一到就被推走）；单消费者串行时插队只保证"排在前面"、**不免除处理时间**。⚠️ 队列已存在时改参数 → **406 PRECONDITION_FAILED**，必须先删队列重建。

### ★★ Graphiti `add_episode` 的 `uuid` 语义（2026-10-12 实测，跨项目通用教训）
- **传 `uuid != null` = 「update 一个【已存在】的 episode」，不是「用这个 id 新建」**。`graphiti_core/graphiti.py:1154-1166` + `driver/neo4j/operations/episode_node_ops.py:140-156`：`get_by_uuid` 查不到 → `raise NodeNotFoundError` → **整个后台 job 静默失败、什么都不写**，而 **HTTP 早已返回 202**。
- 实测三组对照：新 uuid → 240s 内图谱零变化 + 日志 `Background job failed: NodeNotFoundError`；已存在 uuid → 成功（update）；**不传 uuid → 成功（新建）**。
- ⇒ **给这个 API 写"确定性 uuid 幂等"是必死的**（首次投递必然 NodeNotFoundError 且静默丢数据）。**新建一律传 `uuid=null`**。
- ★ 教训普适化：**凡是「客户端指定 id」的写入 API，必须先实测「传一个不存在的 id」会发生什么** —— 很多框架把它当作 `get_or_404`，而不是 `upsert`。
- 连带：`Message.name` 默认空串、完全空闲、可写可持久可查 → 是**确认锚点的唯一可用载体**；`/episodes` 返回 **EpisodicNode 原始序列化（非 DTO）**，含 `uuid`/`name`/`source_description`/`created_at`/`valid_at`，且**排序键是 `created_at`（落库时刻）而非 `valid_at`**。

### ★ 异步链路的「状态机 + 两个定时任务」范式（本轮定稿，可复用）
- **投递 ≠ 落库**：202 只是"已入队"。要确认必须另设对账，且**绝不能在 MQ 消费者里轮询等待**（会占住线程、触发 consumer_timeout 杀连接）。
- **两个定时任务职责必须分开**：① `ConfirmJob` 只管「已投但未确认」（不然它会去扫「没投出去的」，等于把前置过滤器拦下的垃圾从后门灌进去）；② `ReplayJob` 只管「该投但没投出去」（熔断期跳过 / scan 崩溃漏投）。两者都带 `NOT EXISTS(审计表)`。
- **背压熔断的触发信号只能用 MQ 物理积压**（`ready` 计数之和）—— **任何落在数据库里的软状态都会被自己的回滚逻辑清零**，从而"报喜不报忧"。熔断要可自动恢复、要设计成**延迟而非丢弃**（靠 ReplayJob 补投）。
- **「永不重投的终态」必须落一张审计表**（判否 / 毒消息 / 重试耗尽 / 确认超限），否则这些消息会与对账任务**互踢**（对账找不到 → 重投 → 又失败 → 无限循环）。
