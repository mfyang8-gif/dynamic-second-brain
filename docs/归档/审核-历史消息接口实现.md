## 一、为什么做这个

前端切换会话 / 刷新页面后聊天记录丢失（截图里的「后端暂不提供历史消息接口，该会话的过往内容无法回看」）。根因：`chat_message` 表从 V1 起就有数据（流式回答时 user/assistant 消息都落库），但一直没有查询接口，前端只能靠 sessionStorage 缓存本标签页写过的内容。

### 2.4 `service/impl/ChatSessionServiceImpl.java`（新增实现）

```java
@Override
public PageResult<ChatMessageVO> listMessages(String sessionId, ChatMessageQueryDTO dto) {
    // 归属校验：sessionId 必须属于当前登录用户名下的书 —— 不属于直接 403
    getByIdWithOwnershipCheck(sessionId);

    // 大字段说明：content 就是消息本体，历史回看必须要它，无法剥离；
    // 这里显式圈列是为了把 deleted 等内部字段挡在 SQL 层之外。
    Page<ChatMessage> page = chatMessageMapper.selectPage(
            new Page<>(dto.getPage(), dto.getPageSize()),
            new LambdaQueryWrapper<ChatMessage>()
                    .select(ChatMessage::getId,
                            ChatMessage::getRole,
                            ChatMessage::getContent,
                            ChatMessage::getSourcePageIds,
                            ChatMessage::getCreatedAt)
                    .eq(ChatMessage::getSessionId, sessionId)
                    .orderByAsc(ChatMessage::getCreatedAt)
    );

    List<ChatMessageVO> records = page.getRecords().stream()
            .map(this::toMessageVO)
            .toList();
    return PageResult.<ChatMessageVO>builder()
            .total(page.getTotal())
            .page((int) page.getCurrent())
            .pageSize((int) page.getSize())
            .records(records)
            .build();
}

private ChatMessageVO toMessageVO(ChatMessage message) {
    return ChatMessageVO.builder()
            .id(message.getId())
            .role(message.getRole())
            .content(message.getContent())
            .sourcePageIds(message.getSourcePageIds())
            .createdAt(message.getCreatedAt())
            .build();
}
```

> 鉴权复用的私有方法（既有代码，一字未改）——**userId 从线程上下文取，且用子查询把会话锚定到当前用户名下的书**：

```java
private static final String OWNED_BOOK_SUB_QUERY =
        "book_id IN (SELECT id FROM book WHERE user_id = {0} AND deleted = 0)";

private ChatSession getByIdWithOwnershipCheck(String sessionId) {
    String currentUserId = getCurrentUserId();          // ← BaseContext.getCurrentId()
    LambdaQueryWrapper<ChatSession> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(ChatSession::getId, sessionId)
            .apply(OWNED_BOOK_SUB_QUERY, currentUserId); // ← user_id 来自服务端上下文
    ChatSession session = chatSessionMapper.selectOne(wrapper);
    if (session == null) {
        throw new ForbiddenException("无权访问该对话会话"); // → 403
    }
    return session;
}
```

### 2.5 `controller/ChatSessionController.java`（新增端点）

```java
@GetMapping("/sessions/{sessionId}/messages")
@Operation(summary = "分页查询会话历史消息",
        description = "按时间正序返回。鉴权 ID 取自登录上下文，不信任任何前端传入的 userId；"
                + "强制分页（pageSize ≤ 100）；返回 VO，已屏蔽内部字段。")
public Result<PageResult<ChatMessageVO>> listMessages(
        @NotBlank(message = "会话ID不能为空") @PathVariable String sessionId,

    return Result.success(chatSessionService.listMessages(sessionId, dto));
}
```

## 三、数据安全自查结论（审核重点）

| 风险点 | 结论 | 依据 |
|---|---|---|
| **横向越权（拿别人的会话）** | ✅ 已封死 | 归属校验不是简单的 `session_id = ?`，而是叠加子查询 `book_id IN (SELECT id FROM book WHERE user_id = {上下文ID})`。伪造/猜测别人的 sessionId → `selectOne` 返回 null → 403。**实测：陌生 sessionId → 403** |
| **信任前端 userId** | ✅ 不存在 | DTO 无 userId 字段；userId 唯一来源是 `BaseContext.getCurrentId()`（JWT 拦截器写入线程上下文）。**实测：`?userId=888` 被无视，正常返回本人数据** |
| **未登录访问** | ✅ 401 | 走全局 Token 拦截器。**实测：无 token → 401** |
| **无 Limit 全表扫 / OOM** | ✅ 强制分页 | `selectPage` + 上轮已补装的 `PaginationInnerInterceptor`（此前缺失会导致 LIMIT 静默不拼，属系统性隐患，上一轮已修）；`pageSize` 双保险：Bean Validation `@Max(100)` → 400，业务层 Page 参数同源。**实测：pageSize=99999 → 400** |
| **Entity 直接外泄** | ✅ VO 分离 | 返回 `ChatMessageVO`，无 `deleted`；时间 `@JsonFormat` 统一格式。**实测行字段：`content,createdAt,id,role,sourcePageIds` 五个，无多余** |
| **SQL 注入** | ✅ 无风险 | 全部走 MP 的参数化 wrapper；唯一的 `.apply()` 字符串里用户值经 `{0}` 占位符参数化，非拼接 |
| **大字段 IO** | ✅ 已圈列 | `.select(...)` 显式列清单，`deleted` 不进 SQL 结果集。`content` 是消息本体，属业务必需、无法剥离（与工件 `payload` 那种"可剥离的多态大文本"性质不同） |

**一个如实说明**：`chat_message` 表没有 `user_id` 列，归属链是 `chat_message.session_id → chat_session.book_id → book.user_id`。因此鉴权必须先查 session 归属（一次轻量主键查询），再按 `session_id` 分页查消息 —— 不会出现"消息属于 A 用户会话却被 B 拉走"的路径。

## 四、前端配套（让接口真正被用上）

| 文件 | 改动 |
|---|---|
| `api/session.ts` | 新增 `listMessages(sessionId, page=1, pageSize=100)` |
| `types/chat.ts` | 新增 `ChatMessageRecord`（后端 VO 的 TS 镜像） |
| `stores/chat.ts` | `selectSession`：本地缓存优先（缓存里有 references/联想问题，后端 VO 没有）→ 无缓存时 `fetchHistory()` 从后端拉取并写回缓存；`bootstrap()` 不再因"没本地缓存"而放弃续接最近会话 |
| `components/chat/SessionMenu.vue` | 删除「后端暂不提供历史消息接口」toast、「不可回看」徽标与脚注；文案改为"切换到任意会话即可回看" |

**竞态防护**：快速连续切换会话时，`fetchHistory` 落地前检查 `sessionId.value !== id` 则丢弃，防止旧会话的响应覆盖新会话的消息列表。

**已知限制（如实列出）**：后端不落库 `references`（引用来源详情）与 `suggestions`（猜你想问），历史回看时这两栏为空 —— 只有本地缓存过的最近几轮才带全。这是数据模型现状，不是本次接口的缺陷；如需要，后续可在 `chat_message` 加 JSON 列。
