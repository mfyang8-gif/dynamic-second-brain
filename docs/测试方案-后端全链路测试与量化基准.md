# 后端全链路测试与量化基准方案（Phase 4 · v2 重构版）

> **取代**：`docs/归档/测试方案-B1写入链.md`（v1 —— 只覆盖 B1、只有布尔断言、没有"前端发请求"模态）
> **代码基线**：`feat/async-ingestion-pipeline` @ `de3f6a8`
> **目标**：把「新功能是否真的生效」从**布尔断言**升级为**可复现的数字**，并用**与浏览器完全相同的 HTTP 链路**验证。

---

## 0. 本次重构的三处实质变化

| 变化 | v1 方案 | v2（本方案） | 为什么要改 |
| --- | --- | --- | --- |
| **测试模态** | 只有 `@Test`（含 Mockito / 真环境两种） | `@Test` + **HTTP 黑盒（前端同链路）** + **Node 探针** | 用户明确要求"前端发送请求测试"。已用 `ApiHttpSmokeTest` 证明该路线在本工程真能跑 |
| **断言形态** | 全为布尔（`assertTrue` / `assertEquals`） | 布尔 + **量化指标**（时延差 / P50·P95 / 比率 / 位次） | 用户要求"测试量化效果"。布尔断言永远回答不了"到底快了多少" |
| **覆盖范围** | 仅 B1 写入链 | B1 + Phase 3 双路检索 / 两段流式 / SSE + 记忆与习惯 + 跨租户隔离 | "最近新功能"不止 B1；且 B1 的产出（记忆）需要召回侧配合才可验证 |

### 0.1 可行性已证明，不是纸上规划

`ApiHttpSmokeTest`（本轮新增，`@Tag("api")`）**6/6 通过、32.3 秒**，证明四件事：

1. `webEnvironment = RANDOM_PORT` 能起真 Servlet 容器 + 真拦截器链 → **与浏览器发出去的请求是同一条链路**（不是 MockMvc 那种绕过滤器的直连）；
2. **随机端口不会占用 8082** → 用户 IDEA 里跑着后端时本套测试仍可反复执行（这是"能天天跑"的前提）；
3. `/actuator/metrics` 免登可读，且 `graphiti.backpressure.active` 已注册 → **量化有读数入口**；
4. 登录返回的是**裸 JWT**（不带 `Bearer` 前缀）—— 该约定已被断言钉死。

> ⚠️ 该冒烟同时抓到一个**既有 P0 安全问题**（非 B1 引入）：`GET /api/v1/test/mock-login` 无鉴权即可签发 `userId=1` 的 token。见 §7.2。

### 0.2 一条环境铁律（否则测试会静默丢输出）

```bash
-Djava.io.tmpdir=D:/ruoyi/RuoYi-Vue-master/Mini_Nodepad/target/tmp
```

本机 `C:\WINDOWS\TEMP\surefire-*` **建不出临时目录**，surefire 会把测试 JVM 的 `System.out` 整段丢掉 —— 曾因此拿不到附录 D #7 的实测数字。**所有会打印量化数据的用例都必须带这个参数。**

## 1. 测试模态矩阵

三种模态互为补集，缺一种就有一类缺陷永远测不到：

| 模态 | 载体 | 能证明什么 | **证明不了什么** |
| --- | --- | --- | --- |
| **M1 单元 @Test** | JUnit5 + Mockito | 分支、边界值、状态机、静态约束 | 真实 SQL / MQ / 序列化 / 拦截器 / JSON 口径 |
| **M2 HTTP 黑盒 @Test** | `TestRestTemplate`（同步）+ `java.net.http.HttpClient`（流式）+ `RANDOM_PORT` | 鉴权链、DTO 校验与错误码、**真实 JSON 字段口径**、SSE 帧格式、跨租户隔离 | 内部中间态、broker 参数 |
| **M3 真环境集成 @Test** | `@SpringBootTest` + 真 MySQL/RabbitMQ/Graphiti | SQL 可执行性（类型/排序规则/时区）、MQ 拓扑、端到端闭环 | 高并发竞态、broker 内部参数、服务端原始体 |
| **M4 探针（Node）** | Docker API + RabbitMQ Admin API + 直连 HTTP | broker 参数、**真实**队列深度、服务端原始响应体、多路复用流 | 与 Java 代码的一致性（必须回挂一个断言才闭环） |

**贯穿原则**：M1/M2/M3 一律写成 `mvn test` 可**前台跑完**的形态 —— 工具侧起不了长驻服务（`nohup mvn spring-boot:run` 实测会卡死并被回收）。

### 2.2 SSE 事件契约（`ChatStreamService.ChatStreamEvent`）

| `event:` | `data:` 形态 | 用途 |
| --- | --- | --- |
| `status` | `{"phase":"…","message":"…"}` | 步骤条阶段 |
| `message` | JSON 字符串（token） | 正文增量 |
| `notice` | `{"code":"…","message":"…"}` | 本轮可靠性说明（**不被后续 phase 顶掉**） |
| `done` | `{"sourcePageIds":[…],"sourceReferences":[…]}` | 终态 + 引用 |

**`phase` 全集**（断言两段式真的分段了靠它）：
`analyzing_intent` → `retrieving_memory` → `rewriting` → `retrieving` → `web_searching` → `retrieved` → `waiting_web` → `thinking` → `skipped`

### 2.3 量化读数入口（M2 的"数字"从哪来）

| 指标名 | 类型 / 标签 | 回答什么问题 |
| --- | --- | --- |
| `retrieval.dualpath.duration` | Timer `{path=local\|web, outcome=ok\|failed}` | 哪一路慢 |
| `retrieval.dualpath.degraded` | Counter `{path, reason}` | 降级原因分布（reason: `qdrant_error/mcp_timeout/empty_result/all_empty/injection_dropped/no_query`） |
| `retrieval.pass.triggered` | Counter `{pass=pass1\|pass2}` | 两段式是否真的分段 |
| `retrieval.pass.ttft` | Timer `{pass}` | ★ **首字到底降没降，靠它说话** |
| `retrieval.web.guard.dropped` | Counter | 注入防护丢弃量 |
| `retrieval.web.dedup.dropped` | Counter | 语义去重丢弃量 |
| `graphiti.write.queue.depth` | Gauge | 写入侧积压 |
| `graphiti.backpressure.active` | Gauge | 熔断是否生效（**静默熔断 = 静默数据延迟，所以它必须存在**） |

> ⚠️ **前 6 个是惰性注册的**（Micrometer 在首次调用时才创建）→ 冒烟测试里只看到 2 个 `graphiti.*` Gauge。
> 所以量化用例必须**先跑一轮对话再读指标**，且断言写成"读数 ≥ 0 或键存在"，不能写成"列表里必须有它"。

### L5 —— 量化基准（★ 本方案新增，全部产出**数字**）

> 这一层的每条用例都必须**打印一个数**并**断言一个区间**。布尔断言回答不了"效果如何"。

#### L5-1 高危快通道时效提升 `GraphitiFastLaneBenchmark`（M3）

**量**：`chat_message.created_at → graphiti_dispatched_at` 的秒数差
**方法**：连发两条同会话消息，一条含"过敏"、一条中性；各等 20s 后查库
**断言**：高危 < 5s 且常规 ≥ 20s（证明快通道**真的插队了**）；**产出一对数字**
**SQL**：`SELECT TIMESTAMPDIFF(SECOND, created_at, graphiti_dispatched_at) …`

> 这是 B1 里**唯一能把"快通道有用"变成数字**的用例 —— 目前快通道的收益完全是推断。

#### L5-2 优先级插队位次 `MqPriorityOrderBenchmark`（M4 探针，已有基础）

**量**：`priority=10` 消息在 100 条混合消息中的**出队位次**
**断言**：位次 == 1（附录 D #9 已实测为 1，此处固化成可重跑）
**注意**：要求 `write.queue` **无消费者**，否则测的是并发抢夺顺序

#### L5-3 重试分档实际延迟 `MqRetryTimingBenchmark`（M4 探针）

**量**：429 首次重试的**实际**延迟 vs 500 首次重试的实际延迟
**断言**：429 ≈ 120s（档 1）、500 ≈ 30s（档 0），误差 < 10%
**方法**：读消息 `x-death` 头 + 队列 TTL 观测（附录 D #11 已验证 TTL+DLX 保留 priority）

#### L5-4 落库耗时分布（附录 D #7）

**量**：`dispatched_at → synced_at` 的 P50 / P95
**基线**：本轮实测 **≈12.3s**（10s 轮询粒度下的上界，早前记录 15~27s）
**断言**：P95 < 60s
**采集**：`SELECT TIMESTAMPDIFF(SECOND, graphiti_dispatched_at, graphiti_synced_at) …` 取分位

#### L5-5 对账收敛轮次（附录 D #2b 的动态 last_n 效果）

**量**：`graphiti_confirm_rounds` 的分布
**基线**：本轮实测 **0**（首轮命中）
**断言**：P95 ≤ 1 —— 若明显 > 1，说明动态 `last_n` 公式或排序键假设失效

#### L5-6 两段式流式 TTFT（Phase 3）`StreamTtftBenchmark`（M2 流式）

**量**：`retrieval.pass.ttft{pass=pass1}` vs `{pass=pass2}`，以及 HTTP 侧的首个 `message` 时刻
**断言**：pass1 的 TTFT **显著低于**整轮总时长；三路读数（指标 ×2 + HTTP 计时）互相印证
**采集**：`/actuator/metrics/retrieval.pass.ttft`（含 `count/max/totalTime`）

> ★ 这条是"两段式到底有没有用"的**唯一正面证据**。指标里的 `max` 与 HTTP 实测首字偏差过大 → 说明指标打点位置与用户感知不一致。

#### L5-7 双路降级率（Phase 3 可观测性）

**量**：`sum(retrieval.dualpath.degraded) / sum(retrieval.pass.triggered)`
**断言**：正常环境 < 5%；并列出 reason 分布
**采集**：`/actuator/metrics/retrieval.dualpath.degraded`

#### L5-8 检索宽拉取→严过滤的截断比

**量**：`(guard.dropped + dedup.dropped)` 与最终引用条数之比
**断言**：产出比率供调参；**不断言具体值**（依赖外部搜索质量）
**理由**：这是"铁律 5 宽拉取→严过滤→后截断"的**可观测证据**

#### L5-9 跨租户隔离检出率

**量**：L2-2 的 10 条越权尝试中，被正确拒绝的条数 / 10
**断言**：**100%** —— 低于 100% 即阻断发版

### 7.2 ★ 新发现（本方案 L2-1 冒烟时抓到，非 B1 引入）

**`GET /api/v1/test/mock-login` 是完全无鉴权的后门**：

- `TestAuthController` 有 `@RequestMapping("/api/v1/test")`，但**无 `@Profile` / `@Conditional`** → 任何 profile 都生效；

冒烟测试已把它写成 `characterization test`（钉子测试）而非"在夸这个设计"——加固后该用例会红，届时改成反向断言。

**建议**：`@Profile("dev")` 或登记进拦截器并校验，二选一。**建议在 T3 之前定下来**，因为 L2-1 的越权用例会用到这条路径取 token。
