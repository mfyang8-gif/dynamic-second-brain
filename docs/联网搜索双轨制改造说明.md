# 联网搜索双轨制 · 后端改造说明

> 版本：2026-10-12　范围：`Mini_Nodepad`（Spring Boot 3.4 + LangChain4j 1.0.9 + Qdrant + 百炼 WebSearch MCP）
> 关联前端仓库：`mini-notebooklm-web`（本次仅契约与展示分流两处小改，见第 4 节）

---

## 1. 这次到底改了什么（一句话版）

原来系统只有一条「知识库检索 → 主模型作答」的链路，**知识库没料时主模型只能硬答或说"没找到"，却仍然挂着 5 条引用 chip**（用户实测报障）。

现在拆成 **双轨制**，并把「答案来源」做成 **统一溯源**：

| 轨道 | 触发条件 | 行为 |
| --- | --- | --- |
| **轨一 · 意图直达** | 用户问题属于强时效 / 外部事实（今天天气、最新版本、股价、新闻），或显式说"上网查" | **跳过本地 Qdrant**，直接联网预检索后作答 |
| **轨二 · 兜底降级** | 本地检索「没命中」或「命中但没答案」（双层漏斗判定） | 废弃本地结果 → 联网预检索后作答 |

两条轨道共用同一套 **预检索注入管线**：小模型提炼搜索词 → 并发调 MCP 联网 → 把网页摘要**伪装成知识库上下文**喂主模型 → 主模型按普通 RAG 流程流式作答。

**关键点：绝不给主模型挂 Tool。** 我们反而把原来挂在主模型上的 `mcpToolProvider` **摘掉了** —— 挂工具会让主模型进入 Function Calling 思考循环（多一次往返、首字变慢、输出不确定）；改成预检索注入后，联网回答与知识库回答的流式体验完全一致。

回答来源统一成一种结构：

```json
// 本地笔记命中
{"index":1,"title":"...","pageId":"cbe0597a...","chunkIndex":0,"textSnippet":"...","sourceType":"LOCAL_RAG","url":null}
// 外网命中
{"index":1,"title":"红烧肉的家常做法","pageId":null,"chunkIndex":null,"textSnippet":"...","sourceType":"WEB_SEARCH","url":"https://jingyan.baidu.com/..."}
```

前端按 `sourceType` 分流：本地 → 展开分块原文；外网 → 新标签页打开链接。

## 2. 链路总览

```
用户提问
  │
  ├─① 意图路由（qwen-turbo，五分类，带对话上下文 + few-shot）
  │    ├─ WEB_SEARCH ────────────────┐
  │    ├─ KNOWLEDGE_SEARCH / HYBRID ─┤→ ② Query 改写（小模型）
  │    └─ GENERAL_CHAT / EPISODIC ── ┘        │
  │                                          ▼
  │                            ③ Qdrant 检索（RRF：稠密+稀疏融合）
  │                                          │
  │                            ④ ★ 双层漏斗判定（仅 RAG 链路上）
  │                                 ├─ 第一层：纯稠密【余弦】top 分 < 0.35 → 判未命中
  │                                 └─ 第二层：qwen-turbo 判卷 True/False
  │                                          │
  │                       放行 ◄─────────────┴─────────────► 降级
  │                        │                                   │
  │                        │                    ⑤ 预检索注入（两轨共用）
  │                        │                       搜索词并发 → 百炼 WebSearch MCP
  │                        │                       → 域名打散 → DashScope Rerank
  │                        │                       → 组装「网页来源 [n]」上下文
  │                        ▼                                   ▼
  └──────────────► ⑥ 主模型流式作答（统一 streamAnswer，含落库/摘要/推荐）
                               │
                               └─ SSE：status(web_searching) → message… → done(sourceType/url)
```

SSE 阶段序列（前端按到达顺序渲染，允许跳跃）：

- 轨一：`analyzing_intent → rewriting → web_searching → thinking`
- 轨二：`analyzing_intent → rewriting → retrieving → retrieved → web_searching → thinking`
- 正常命中：`analyzing_intent → rewriting → retrieving → retrieved → thinking`（**没有** `web_searching`）

### 3.3 ChatStreamService 的六处接线

1. **依赖注入**：新增 `QdrantTemplate`（走原生稠密通道）、`RagRelevanceJudgeService`、`WebAugmentService`。
2. **路由分流**：`switch` 新增 `case WEB_SEARCH -> handleWebSearchChat(...)`（轨一：跳过 Qdrant）。
3. **双层漏斗**：新增 `evaluateRagFallback()` —— 第一层 `topCosineScore()` 走
   **纯稠密余弦通道**；第二层调 `ragRelevanceJudgeService.isRelevant()`。
4. **预检索入口**：新增 `runWebAugment()` —— 先下发 `web_searching` 状态，再调 `WebAugmentService`；不可用时降级为 `NO_SOURCE_CONTEXT`（模型自有知识 + 强制声明）。
5. **流式尾巴抽取**：把原 `handleRagChat` 后半段抽成 **`streamAnswer(...)`**，RAG / 轨一 / 降级三条路共用（落库、摘要、推荐、中断、错误处理只写一份，避免漂移）。
6. **done 契约扩展**：`doneEvent(List<String>, List<SourceReference>)` 序列化时带上 `sourceType` 与 `url`。

### 3.4 ⚠️ 最容易踩的坑（本次实测踩到并已规避）

**RRF 分数 ≠ 余弦相似度。** 主检索链路走 RRF 融合，返回的是**排名制分数（典型 0.01~0.03）**；
拿它跟 0.35 的阈值比会**100% 误判成"未命中"**，把每一条正常问答都赶去联网。
所以第一层阈值**必须**走 `QdrantTemplate.searchByDenseSimilarity()` 那条原生稠密通道（返回真实余弦 0~1）。
实测某次日志：

```
联网降级·第一层阈值拦截 | topCosine=0.2674532, gate=0.35
```

## 4. 配置项速查

```yaml
rag:
  web-fallback:
    enabled: true                # 总开关：关掉即完全回到"只答知识库"的老行为
    cosine-gate-threshold: 0.35  # 第一层纯余弦底线（只对纯稠密通道有效）
    judge-enabled: true          # 第二层 qwen-turbo 判卷（牺牲 ~0.5-1s 换"绝不乱答"）
    judge-timeout-ms: 3000       # 判卷硬预算，超时放行走原 RAG
    judge-max-chunks: 4          # 判卷最多喂几条片段

web-search:
  pre-search-limit: 5            # 单条搜索词取回几条网页
  pre-search-max-queries: 2      # 最多并发几条搜索词
  pre-search-context-top-n: 5    # 最终注入上下文保留几条来源
  pre-search-timeout-ms: 8000    # 单路搜索等待上限

qdrant:
  collection-name: dynamic_brain # 第一层快筛也要指名集合
```

**回滚方式**：把 `rag.web-fallback.enabled` 设为 `false` → 立即回到改造前的行为（不联网、不判卷），
前端契约仍兼容（旧引用没有 `sourceType`，按 `LOCAL_RAG` 渲染）。

### 5.2 关键观测

1. **轨一确实省掉了一次 Qdrant 往返**：S1/S2 的阶段序列里**没有** `retrieving`，`web_searching` 紧跟 `rewriting`。
   这正是新增 `WEB_SEARCH` 意图分类的收益 —— 时效问题不再先白烧一次本地检索与数秒延迟。
2. **轨二保留了完整的判别痕迹**：S3/S4 都先走完 `retrieving→retrieved`，才转 `web_searching`。
   说明「先试本地、不行再降级」的漏斗没被绕过，也没提前短路。
3. **不打乱正常问答**：S5 全程没有 `web_searching`，TTFT **11.2s**，明显快于联网轮（21.8~35.1s）；
   S6 闲聊 TTFT 仅 **4.2s** 且零检索零引用 —— 资源管控目标达成。
4. **★ S4 是最有价值的一条**：该问题里含「首版」「知识库」等笔记高频词，**向量分数并不低**，
   但笔记里确实没有"用哪种数据库/向量库"的答案。**只有第二层判卷器能识破"同主题但无答案"** ——
   这就是当初坚持在阈值之外再加一层 LLM Judge 的实证理由。
5. **溯源字段完整往返**：S8 从 DB 读回的引用 `sourceType` 全为 `WEB_SEARCH`、`url` 无一缺失、
   `pageId`/`chunkIndex` 均为 `null` —— 紧凑构造器的 `LOCAL_RAG` 兜底**没有误伤新数据**。
6. **声明句生效**：S1/S3/S4 的回答首句均为
   「未在你的笔记中找到相关内容，以下回答基于全网搜索与我的通用知识。」——
   提示词里的"声明句例外"条款与 `WebAugmentService` 的强制指令配合正常，模型没有隐瞒来源。
